# 踩坑与经验交接（LESSONS）

> **用途**：本项目（明日方舟强度评测）跑完一轮后，把**可迁移**的经验与踩坑固化下来。
> 写这份文档的直接目的是给**下一个项目**（`E:\github\pet` 单机游戏角色陪伴 Agent）当起点，
> 但内容本身与游戏无关 —— 都是 AI Agent / 数据管线 / 数值系统类项目的通用教训。
>
> **怎么读**：每条都写了「现象 → 根因 → 做法」。赶时间只读 §1（AI 相关）与 §6（自查清单）。

---

## 0. 一句话总结

**这个项目踩的坑，八成不是"算法不会"，而是三类**：

1. **模型/子代理说的话不可信**，而我没有验证就采信了
2. **我说的话不可信** —— 没核实就下结论（"数据里没有""未建模"）
3. **验证体系有盲区** —— 真实存在一个 bug，逃过了当时全部测试

下面按这三条展开。

---

## 1. AI / Agent 相关（最重要，直接可迁移）

### 1.1 模型输出必须"可核验"才采信 —— 子代理编造过 id

**现象**：派子代理读游戏数据做语义分类，它交付的 JSON 里有 4 条 `id` 是**编造的**。
真实的打字机 id 是 `token_10026_bgsnow_subbow`，它写成 `token_10014_...`；另外 3 条同批错误。

**根因**：模型在"结构化输出"这种任务上会**保持格式正确但内容编造** ——
格式越像样，越容易骗过验收。

**做法**（已落地成机制）：
- **不采信模型给的键**（id / 字段名 / 路径），改为**按 `owner+name` 这类语义对确定性关联**
- 要求每条结论附带**原文引用**，且引用必须能在源数据里检索到；引用与结论不对应的一律丢弃
- 交付物标注**可信度分级**（`phrase` = 有原文佐证 / `inferred` / `default` = 裸假设）

**可复用的一句**：
> 模型只能**提出线索**，落到数据/代码里的键必须由确定性逻辑重新解析一遍。

### 1.2 模型输出必须"可拒绝"，且默认不入库

**现象**：子代理把麦哲伦的无人机判成"技能绑定"，但**引用的句子是电弧的** ——
它把 A 干员的证据贴到了 B 干员的结论上。这类错误光看结论看不出来。

**做法**：
- 架构上分层：**规则层负责数值与确定性解析**，模型层只处理长尾
- 模型产出**存入待审表**（`mechanism_parses`），可导出审核片段，
  **绝不自动注入计算引擎** —— 未经审核的输出不影响任何数值
- 报告里明确写"哪些数字来自模型、哪些来自数据"

**可复用的一句**：
> 把"模型提议"和"系统采信"之间加一道**人工/确定性闸门**，是 Agent 工程里性价比最高的一条防线。

### 1.3 用 LLM 做"分类/抽取"时，判据要以**描述文本**为准，别猜字段名

**现象**：想筛"能造成伤害的召唤物"。我先用"有 `atk_scale` 倍率键"作判据 ——
结果一次命中 19 条，**其中 16 条是错的**（那是"一次性引爆伤害"，不是普攻倍率）。
反过来，Mon3tr / 令 / 乌尔比安这些**纯普攻**召唤物压根没有倍率键，全被漏掉。

**根因**：**字段名与语义不是一一对应**。同一个 `atk_scale` 在不同上下文里是不同东西。

**做法**：
- 判据**多条并列**（结构信号 + 数值范围 + 文本语义），缺一条就会错一批
- 关键判据要能**说清"为什么排除"**，并存进数据里（`reason` 字段），便于事后复核
- 我最终的方案是**显式排除清单 + 通用规则**：能被通用规则覆盖的进规则，剩下的人工核对后**列白名单**并注明依据

### 1.4 别让模型做"数值/频率"假设

**现象**：召唤物的"同时存在数"一度想用天赋里的 `cnt`（"可以使用 5 个"）。
实际上那是**持有总数**，不是同时在场上限；而且令/麦哲伦的召唤物是**"技能功能模式"**，
同一时刻只有 1 种在场 —— 按 5 或 3 算就是** 3～5 倍高估**。

**做法**：
- 频率/数量类参数**只认直接证据**（原文点名该对象的那句"最多存在 N 个"）
- 拿不到就直接**取保守值并标注为假设**，绝不用"看起来相关"的数字顶上
- **给不出 DPS 的就别给 DPS**：一次性触发伤害只报"每次触发"的量，
  触发次数属玩法层 —— 强给一个频率等于**把假设伪装成事实**

**可复用的一句**：
> 拿不准的参数，输出"区间 + 假设说明"，比输出一个精确的错数有价值得多。

## 2. 数据与出处（第二重要）

### 2.1 "数据里没有"是最容易犯的错 —— 先 `Object.keys()` 再下结论

**同一类错，我犯了三次**：

| 我说过 | 实际 | 根因 |
|---|---|---|
| "射程几何未建模，只有 id 没有形状" | `range_table.json` **一直就在**数据仓库里，73 个范围带完整坐标 | `rangeId` 在 `phases[n].rangeId`（相位级），而构建脚本只读了 `attributesKeyFrames.data` |
| "元素损伤数值来源 PRTS" | 就在游戏数据的 `gamedata_const.json` → `termDescriptionDict` | 它**以中文描述文本存放**，不是独立数值字段；我只查了顶层键 |
| "基础分支特性游戏数据里不存在" | 在 `character_table` 的**干员级 `description`** | 我只读了 `trait` 字段 |

**做法**（已成习惯）：
- 判断"某数据是否存在"前，**先把实际字段名 dump 出来**：`Object.keys()` 逐层打到叶子
- 区分"不存在"与"在别处"：前者要穷尽搜索，后者只需换个字段
- 写进结论时用**可验证的措辞**："在 X 文件的 Y 字段中找到"，而不是"数据里没有"

**可复用的一句**：
> 说"这个数据没有"之前，先证明**你找过了**。否则它只是"你没找到"。

### 2.2 出处要写"谁维护的 + 怎么来的"，不能写"官方"

**现象**：我在 README 写"数值来自游戏客户端数据，每一项都能追到出处"。
用户追问后核实：`Kengxxiao/ArknightsGameData` 是**第三方在 GitHub 上维护的提取仓库**，
不是官方源；而且那句话还把**我自己拍的场景假设**（受击频率 0.5 次/秒、陷阱按全部触发、
冷却≈持续秒数）一起罩进去了。

**做法**：
- 出处写到**仓库名 + 维护性质**（"第三方维护的客户端数据提取"），不写"官方/客户端"
- 严格区分两类数字：
  - **有出处的**（数据集字段 / 对账过的 wiki）
  - **我的假设**（场景参数、覆盖率、频率）→ **单独一栏列出，明确写"无数据出处"**
- 报告里对每个未计入项显式标注 ⚠

### 2.3 条件型数据必须连**适用条件**一起提取

**现象**（真 bug，且逃过了当时全部测试）：
- 泥岩「受到来自**【萨卡兹】**敌人的伤害降低 30%」
- 止颂「阻挡时，受到来自**非自身阻挡敌人**的伤害降低 35%」

两条都被当成**对所有敌人**生效 → 承伤偏低、生存偏高。
泥岩 vs 物理精英：**每击 278（应为 398）· 可挨 15 击（应为 10 击）· 39.0s（应为 26.0s）**。
即**生存能力被高估约 50%**。

**做法**：
- 数值与限定语（势力/位置/状态/概率）**成对提取**，条件不满足就是"白送加成"
- 统一原则：**条件型加成一律不进基准值**，单独列出并给"条件满足时"的对照值
- 加断言把"条件型不得进基准"锁死

**可复用的一句**：
> 项目里凡是"看起来无条件生效"的数值，都要问一句：**它的适用条件在哪？**

## 3. 数值系统（有数值就算数的项目都适用）

### 3.1 用**离散**模型，不要用连续近似

**现象**：生存时长原本写 `血池 ÷ 每秒承伤`。1758 血 vs 2520/击 → 算出 4.9s，
**实际是 1 击即倒**。连续模型把"这一下能不能扛住"抹平了。

**做法**：逐次受击 + 击间回血/恢复的**离散模拟**。同理"多敌人集火"要按
**同时命中 = 每击 ×N、间隔不变**，而不是 `间隔 ÷ N`（后者平滑化伤害，高估 60%+）。

### 3.2 多副本/多目标类参数，先问"同一时刻能有几个"

**现象**：召唤物按"持有 5 个"算 → 3～5 倍高估（见 §1.4）。
同类坑在别处也常见：多目标 DPS 按"范围内敌人数量"乘。

**做法**：把**空间量**（覆盖格数/目标数/射程形状）与**时间量**（频率/覆盖率）分开报，
**不并进单目标基准值**，否则等于假设"敌人永远站满范围"。

### 3.3 通道互斥要显式声明，否则会双算

**现象**：陷阱类召唤物的伤害已归 `trap` 通道，若再进 `summon` 通道就是**重复计算同一份伤害**。

**做法**：通道之间写**显式排除表**，并加断言"两者不同时命中"。

### 3.4 减伤/减免的作用顺序要统一

**现象**：召唤物减伤一度写成"先算 DPS 再减防"，丢掉了 5% 下限，结果 501 变 301。

**做法**：**减伤作用在"每击伤害"上，再除以间隔**；与主伤害公式同一口径，不要另起一套。

## 4. 验证与测试

### 4.1 断言写太宽 = 没写

**现象**：早期写过 `ok === true || Array.isArray(errors)` —— 校验失败也被放过。

**做法**：断言必须**唯一确定**通过条件；宁可多写几条。

### 4.2 套件多 ≠ 覆盖全（**这次最痛的教训**）

**现象**：条件型减伤那个 bug（§2.3）逃过了当时**全部 7 套测试**。
根因是：**没有任何断言覆盖"减伤/生存"这个维度** —— 测试数量多给了我虚假的安全感。

**做法**：
- 每加一个维度，就**同步加一个该维度的断言套件**（这次补了 `verify-survival.mjs`，17 条）
- 定期问自己：**"哪个功能是完全没有测试碰过的？"** —— 那才是风险最高的地方
- 数值项目的必备套件：公式正确性 / 通道互斥 / 边界（0 值、极值）/ **契约（输出结构）/ 零漂移**

### 4.3 "数值零漂移"是数值项目最好的回归指标

**做法**：同一输入无论走哪条路径（JSON→工具链 / DB→API），结果必须与**锚点表**完全一致。
锚点是硬编码的期望值，改动数值逻辑后必跑。

另外：**重建全链路要验证"数据零漂移"** —— 我重建一次数据集，除时间戳外**零改动**，
这才敢说管线可复现。

### 4.4 每条断言都要能手工验算

**做法**：断言里写算式而不是常量，例：
`assert('Mon3tr = 1402/2.0 = 701', summonDps(op) === 1402/2)`

### 4.5 反向断言：确认"错误的东西不存在"

**现象**：简历里我写了"12 类表述"，实际是 10 类（查代码才发现）。
如果只有正向断言，这种错不会被发现。

**做法**：关键错误值加**反向断言**（`must NOT contain`）。简历/文档类产物尤其需要。

## 5. 工程与环境（Windows / 国内网络环境下踩的）

| 坑 | 现象 | 做法 |
|---|---|---|
| **PowerShell 改含中文的文件** | `Set-Content` / 内联 `node -e` / `.ps1` 里写中文 → **编码被打乱** | 一律用文件写入工具；`.ps1` 必须存成 **UTF-8 带 BOM**，或**脚本里不写中文**（用 ASCII 标记 + 数据文件承载中文） |
| **PowerShell 5.1 读 `.ps1` 默认 ANSI** | 脚本里的中文路径变乱码，报"找不到路径" | 存 UTF-8 **BOM**；或改用 `.mjs`（Node 默认 UTF-8） |
| **`\uXXXX` 在单引号字符串里不转义** | 生成的路径里出现字面 `\u6c42` | 别用 `\u` 转义拼中文；用双引号或用数据文件 |
| **失效代理导致 npm/git 全挂** | `~/.npmrc` 与 git 全局写死 `127.0.0.1:7897` → `ECONNREFUSED` | 清掉代理配置；git 用 `-c http.proxy= -c https.proxy=` |
| **`vite build` 不做类型检查** | 构建成功但类型是错的 | 同时跑 `tsc -b` |
| **Windows 文件占用** | 服务在跑时重建 SQLite → `EPERM` | 重建前先停服务；脚本里给**明确的错误提示**而不是抛原始异常 |
| **`git add -A` 会带上临时产物** | 我把临时改名的前端 `dist` 误提交了 | 提交前 `git status` 逐个确认；临时目录名要进 `.gitignore` |
| **终端显示乱码 ≠ 文件坏了** | Node 抛的 UTF-8 中文错误在 PowerShell 里显示为乱码 | 用「读文件」验证，别被终端显示误导 |

## 6. 自查清单（每次交付前过一遍）

**关于"我下的结论"**
- [ ] 说"数据不存在/未建模"之前，我**dump 过实际字段**了吗？
- [ ] 出处写清"谁维护、怎么来的"，没写"官方"吧？
- [ ] 我自己的**假设值**是否与"有出处的数据"分栏列出了？

**关于"模型/子代理给的结论"**
- [ ] 它给的**键**（id/字段/路径）我重新确定性解析过了吗？
- [ ] 它的引用**真的支持它的结论**吗（不是贴错句子）？
- [ ] 产出是否**默认不进入生产逻辑**、需要审核？

**关于"数值"**
- [ ] 条件型加成有没有**连条件**一起提取？进基准了吗（不该进）？
- [ ] 空间量（目标数/范围）是否被并进了单目标基准？
- [ ] 用了离散模型还是连续近似？
- [ ] 通道之间会**双算**吗？

**关于"测试"**
- [ ] 这次新增的维度**有断言覆盖**吗？
- [ ] 有没有哪个功能**完全没被测试碰过**？
- [ ] 锚点表跑了吗？数据重建后**零漂移**吗？
- [ ] 关键结论有**反向断言**（错误值必须不存在）吗？

**关于"给用户的话"**
- [ ] 有没有把**给 agent 看的旁白**（口径说明、内部假设）混进用户界面？
- [ ] 未计入/未建模项是否显式标注了 ⚠？

## 7. 对下一个项目（`E:\github\pet`）的直接建议

「单机游戏角色陪伴与攻略 Agent」与本项目不同 —— 它是**多模态 + 长会话 + 角色一致性**，
数值不是核心。但上面前四条仍然直接适用，重点会变成：

1. **角色一致性 = 本项目的"条件型数值"**：人格设定/口吻/记忆的**适用条件**（场景、情绪、进度）
   要与内容成对维护，别让模型自由发挥
2. **日志解析 = 本项目的"数据管线"**：结构化抽取要有 schema + 校验 + 可拒绝，
   **模型抽取的字段必须可核验**（回到 §1.1）
3. **攻略建议 = 本项目的"数值结论"**：区分"数据支持的"与"模型推测的"，
   推测部分要标注来源与置信度
4. **长会话记忆**：需要**明确的写入/召回策略**，而不是把历史全塞进上下文 ——
   等价于本项目的"通道分流"
5. **多模态串联**（文本+图像）：沿用 §4.1 的思路 ——
   **每一段链路都要有可复现的输入输出样本**，否则出错无法定位

**先立三样东西再写功能**：
- `docs/` 里的**恢复文档**（新会话读它就能接上）
- **锚点/样本集**（固定输入 → 期望输出，用于回归）
- **测试套件骨架**（哪怕一开始只有几条断言）
